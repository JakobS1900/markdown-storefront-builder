# Phone-sized usability audit of the menu prototype

Date: 2026-10-01. Branch: `032-menu-first-workflow` at `8fd92e2` before this iteration.

## Method

I used the running Vite app in isolated Chrome storage at 390 by 844 CSS pixels. I created Ceramics with three offers, added Prints with one offer, opened Preview, returned to Build, and pasted a three-line mixed-syntax price list into Prints. Each browser control was focused before input or click, so blur and repaint followed the same path as a normal keyboard and tap. The browser reported zero runtime exceptions and no document-width overflow in these runs. I also opened the installed `0.13.0-test.1` APK on the connected SM_T700, Android 6.0.1, and viewed its saved Ceramics menu in Preview and Build. The tablet was awake immediately before each screenshot.

The baseline images are [blank page](media/2026-10-01-ux-first.png), [three-item editor](media/2026-10-01-ux-three-items.png), [mixed paste review](media/2026-10-01-ux-paste-review.png), and [tablet editor](media/2026-10-01-ux-tablet-open.png). These are synthetic menus and isolated browser data, not a private seller menu.

## Observations

1. The first phone screen presented Page title, four start buttons, a template disclosure, and six generic section buttons. `Create a menu` and `Paste a page you already have` were the tasks this seller needed, but they competed with wizard, example, templates, and data-model choices. The generic choices were also in a sticky strip above the three bottom tabs.
2. A new one-item menu had a document height of 1,211 pixels at 390 by 844. The three-item editor reached 2,010 pixels. In the captured three-item view, the second and third item cards filled the working area while the six generic choices took two rows above the tab bar. Category, Item, and Price were correctly editable together, but the repeated cards and persistent strip still made the flow feel long.
3. The four-item menu did preserve Ceramics, Handmade mug `$28`, Planter `from $35`, Custom plaque `Ask me`, and Prints in Preview. This run found friction, not a data-loss failure in manual entry.
4. The mixed paste `Woven basket, $24`, `Hand-dyed scarf: from $35`, `Cotton tote | $18` showed all three source lines and all prices, but proposed `Woven basket,` and `Hand-dyed scarf: from` as item names. The review only offered a checkbox per line. A seller could not correct just a proposed name or price in that review. The whole-paste delimiter choice in `readCandidates` selected pipe on a tie, then the other lines used a last-number fallback. That explains both malformed names and the missing `from` in the second proposed price.
5. The Android 6 tablet rendered the saved Ceramics item and the current menu form. The tablet screenshot shows the same generic section strip, though its wider viewport keeps it to one row. This is a layout observation, not evidence that a seller can complete tasks without help.

## Design decision for this iteration

Put the two likely start tasks first, keep secondary starts and other section types behind clearly named disclosures, and make the price-list review correctable before Add. Keep source lines visible and keep interpretation edits in a draft until Add. The saved page format and compiler already support the needed names and prices. The broader multi-section correction panel in feature 030 is still separate work.

This follows the [Nielsen Norman Group guidance on progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) for showing frequent actions first while keeping advanced actions discoverable. The review also keeps visible labels, consistent with [Baymard's mobile form findings](https://baymard.com/research-articles/mobile-forms-avoid-inline-labels). Those sources support the design direction; the measurements and parser defect above come from this app's own run.

## What remains unproven

The five real seller sessions in `specs/032-menu-first-workflow/spec.md` have not happened. Automated and solo browser runs can verify task paths and values but cannot establish that new sellers understand them, trust the interpretation, or finish faster. Record time, help, corrections, and wrong values with `2026-10-01-seller-task-script.md` before a usability success claim or normal release.

## Iteration result

The blank Build screen now offers Create a menu and Paste a page you already have first. Wizard, example, templates, private title, and the other section types remain in named disclosures. Once a menu exists, the six generic choices no longer fill the persistent phone dock. The [320 pixel start](media/2026-10-01-ux-after-320-first.png) and [390 pixel start](media/2026-10-01-ux-after-390-first.png) show the result.

Price-list review now shows editable Item and Price fields under each selected source line. The mixed example proposes Woven basket at `$24`, Hand-dyed scarf at `from $35`, and Cotton tote at `$18` without punctuation attached to names. Changing only the second row to Hand-dyed silk scarf at `from $40` carried those exact values into [Preview](media/2026-10-01-ux-after-320-preview.png) and Copy. The [320 pixel correction view](media/2026-10-01-ux-after-320-paste-review.png) has visible labels and a reachable Add button. Both 320 and 390 CSS pixel browser runs reported document `scrollWidth` equal to viewport width at every captured step and zero runtime exceptions.

Review found three further failure paths that solo tapping had not exposed. A checked row whose corrected Item was blank could otherwise be omitted while Add promised to include it, so Add now blocks with the source line number until it is corrected or unticked. Lines beyond the first 100 now have a review page instead of being permanently hidden. Delayed file reads now survive unrelated review choices but cannot overwrite source text changed in the meantime or a later paste session. The whole-page review also keeps section 101 visible and focused when its checkbox changes. Closure review found that activating its section pager dropped keyboard focus, so the next page now focuses its first section checkbox; the 102-section regression checks that transition.

The focused tests reproduced those defects before the fixes. The menu and price-list suite passed 94 tests, and the later paste and sidebar suites passed 54 and 42 tests respectively after the changes. The full `npm run verify` exited 0 with 89 test files and 1,762 tests, 63 accessibility tests, clean light and dark contrast, menu-file export, and the PWA update gate. The contrast gate initially saw six offscreen formatting buttons as incomplete; its real-browser pass now scrolls those controls into view before measuring, and all six were measured in each palette.

The first signed `0.13.0-test.1` iteration APK built with JDK 21 (`BUILD SUCCESSFUL in 1m 35s`), installed on the SM_T700 with `adb install -r` returning `Success`, and opened with WebView 106 on Android 6.0.1. I pasted `Basket, 24`, changed the reviewed price to `240`, added the item, and saw `Basket` at `240` in Preview and the copied Markdown. After force stop and relaunch, Build still showed `Ceramics, 2 items`. I named this synthetic test page `DeviceQA`; the page drawer then showed both `DeviceQA` and the pre-existing `Untitled page`.
