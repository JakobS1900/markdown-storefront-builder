# Data model: The menu file

**Feature**: 024-menu-file
**Date**: 2026-09-06

Two stores change and one gains a sibling. The document contract goes to version
4, and the browser database gains a second object store holding bytes, which is
the first time this app has stored anything that is not text.

---

## 1. The document contract, version 3 to 4

`engine/src/document/descriptor.ts`. Order is normative, so each addition below
states where it goes and why.

### `MENU_TIER_FIELDS`

Add one field, positioned **immediately after `imageUrls` and before `cost`**:

| Name | Type | Required |
|---|---|---|
| `localImageIds` | `stringArray` | no |

Placed beside `imageUrls` because that is the field it is the sibling of, and a
reader of a saved page should find the two kinds of picture together.

### `GALLERY_ITEM_FIELDS`

Add one field, **after `imageUrl`**:

| Name | Type | Required |
|---|---|---|
| `localImageId` | `string` | no |

Singular, because a gallery item is one picture. `imageUrl` stays `required`
and may be the empty string, which is what an item carrying only a local
picture holds. The descriptor already permits this: `nonEmpty` appears on
exactly two fields in the whole schema, `id` and `target`, and content fields
deliberately allow an empty string.

### `BLOCK_FIELDS.profile`

Add one field, **after `avatarUrl`**:

| Name | Type | Required |
|---|---|---|
| `localAvatarId` | `string` | no |

### Why these are identifiers and not addresses

FR-089. The obvious cheaper design is to put `mdsb-asset:<id>` straight into
`imageUrls` and change no schema at all, which would cost nothing and needs no
migration. It is rejected deliberately.

`imageUrls` is a field every existing and future code path reads as "addresses
that can be published". Putting something unpublishable in it makes every one
of those paths wrong by default and correct only if it remembers to check. A
separate field makes the same code wrong only if it goes looking for trouble.

The precedent is `cost`, which the descriptor already carries as a field the app
uses and the compiler is forbidden to emit, guarded by its own test. These
fields follow it exactly.

### Migration, version 3 to 4

`engine/src/document/migrate.ts`, appended to `MIGRATIONS` as
`{ from: 3, to: 4, apply }`.

The step **sets the version stamp and changes nothing else.** It must not create
any of the three new fields, even as an empty array or an empty string.
`migrate-tier-ids.test.ts` states the rule and tests it for `cost`: "an absent
optional field is never defaulted into existence, or round tripping would depend
on which representation the writer happened to pick." FR-090 restates it and the
new fixture asserts it.

A version 3 page therefore comes forward carrying exactly what it carried, which
is what makes SC-008 hold: no field lost, no field invented, and identical
output for every paste host, because the emitters see nothing new.

### What this obliges

- `engine/tests/document/parity.snapshot.json` regenerated by `npm run snapshot`,
  and the diff read rather than accepted. Three added field specs and one
  changed `schemaVersion`, and nothing else, is what a correct diff looks like.
- A `v3-*.json` fixture under `engine/tests/document/fixtures/`, since Principle
  III requires a fixture per version step.
- Round trip coverage for a page carrying all three new fields.

## 2. The picture store

`app/src/db.ts`. `DB_VERSION` 1 to 2, adding one object store beside `pages`.

**Store**: `assets`, `keyPath: "id"`, no indexes.

| Field | Type | Meaning |
|---|---|---|
| `id` | `string` | The identifier a document refers to. Minted in the app, never in the engine. |
| `blob` | `Blob` | The picture, after `normalise()`. |
| `mime` | `string` | One of a fixed set. See below. |
| `bytes` | `number` | `blob.size`, denormalised so the storage view can total without reading every blob. |
| `createdAt` | `number` | For ordering the storage view only. Never reaches the engine, which Principle I forbids from reading a clock. |

`pages` is untouched, including its deliberate decision to hold `json` as text so
that a page this version cannot validate can still be handed back as its exact
bytes under FR-018. Nothing about this feature may disturb that.

### Accepted types

`image/png`, `image/jpeg`, `image/webp`, `image/gif`. Checked at storage time,
not at display time.

**`image/svg+xml` is refused.** An SVG is a document that can carry script, and
although a browser does not run script in an SVG loaded through `<img>`, the
saved menu file is a document that leaves this app and gets opened by other
people in contexts we do not control. Principle IV's narrow gate says allow list,
not deny list, and there is no seller need this excludes: `normalise()` re-encodes
through a canvas and would turn an SVG into a raster anyway.

### Invariants

- A stored asset is immutable. Editing a picture means storing a new one.
- Nothing deletes an asset except an explicit action by the seller. D6, FR-087,
  and the rule `db.ts` already states for `pages`.
- A document may reference an asset id that no longer exists. That is a normal
  state, not corruption: FR-088 requires the page to still open and the menu
  file to still be produced, reporting the missing picture by name.

## 3. The compile-side capability

`engine/src/compile/capabilities.ts` gains one field on `Capabilities`:

| Name | Type | Meaning |
|---|---|---|
| `localImages` | `boolean` | Whether this host can display a picture held on the seller's device. |

`Target.sources` is `Record<keyof Capabilities, string>` with no optional keys,
so every existing target must gain a citation for it. That is the type system
enforcing FR-014, and it is why adding a capability is deliberately not free.

| Target | `localImages` | Citation |
|---|---|---|
| `PORTABLE` | `false` | A specification describes text. It cannot carry a file from somebody's phone. |
| `RENTRY` | `false` | A paste host receives text. Nothing in that text can reference a file on the seller's device. |
| `TEXT_IS` | `false` | As above, and its stated 200000 byte page limit makes embedding bytes impossible even in principle. |
| `MENU_FILE` | `true` | Observed in our own renderer, which is the thing that displays this file. Stronger evidence than any of the three above carry. |

### `TARGETS` and `ALL_TARGETS`

Keeping `MENU_FILE` out of the `TARGETS` array is right for the host picker and
**wrong for the test suite**, and the analysis pass caught it before any code
was written.

Seven engine test files iterate `TARGETS` to assert something across every
target: `golden`, `determinism`, `performance`, `compile`, `holistic`,
`holistic-003` and `cost-never-published`. A target outside that array is
silently outside all seven. So the one output that carries embedded pictures
would have had no golden file, no determinism check, no performance budget and
no cost guarantee, and every one of those tests would have stayed green while
covering nothing.

That is the same shape as the gate this project already shipped which "would
have compiled nineteen documents that carry no `cost` between them and passed
forever".

So the array splits in two:

| Name | Contents | Used by |
|---|---|---|
| `TARGETS` | `PORTABLE`, `RENTRY`, `TEXT_IS` | `findTarget`, the host picker, and any sweep whose subject is "places a seller pastes a page" |
| `ALL_TARGETS` | `TARGETS` plus `MENU_FILE` | Every sweep whose subject is "everything the compiler can emit" |

`findTarget` keeps searching `TARGETS` only, so a page whose stored `target`
reads `menu-file` still falls back to `PORTABLE` with a warning, which is the
safe direction and the behaviour D2 wanted.

Choosing between the two is now a decision a reviewer can see, which is the
point. `cost-never-published` takes `ALL_TARGETS`, because a cost must never
appear anywhere. `local-image-never-published` takes `TARGETS` for its absence
half and `MENU_FILE` alone for its presence half, because that pair is what
makes it discriminating.

### The emitted form

For a target with `localImages: true`, a local picture is emitted as an ordinary
Markdown image whose address is `mdsb-asset:<id>`.

Short and deterministic, so compiled output stays the size it has always been
and the `size_limit_exceeded` byte count stays meaningful. The app resolves
these on the rendered DOM. Bytes never enter the markdown and never pass through
either address check. D3 has the full reasoning.

For a target with `localImages: false`, the picture is dropped and
`local_image_unsupported` is raised naming it, which is the declared fallback
Principle II requires of every capability.

### The new diagnostic

`local_image_unsupported`, severity `warning`, added to the code union in
`engine/src/compile/diagnostics.ts`.

Its message names the picture and says where it does appear, so it reads as a
signpost rather than a scolding. It must not contain the asset id, the original
filename, or anything else identifying the file: FR-081, and the same reasoning
`cost-never-published.test.ts` applies when it checks that a cost does not leak
into a diagnostic either, because a warning is somewhere a seller might
screenshot.
